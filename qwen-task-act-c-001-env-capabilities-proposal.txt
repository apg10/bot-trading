OBJETIVO
========

Definir el contrato canónico de **capacidades estáticas** (entorno y capacidades) que
UI, IA y backend deben compartir, garantizando compatibilidad con el endpoint existente
`GET /api/capabilities`. Este slice se limita a campos derivables sin diagnóstico en
tiempo de ejecución: entorno, soporte de subsistemas y versión del schema.

**Fuera de alcance**: aptitud de datos, disponibilidad de ejecución, catálogo dinámico,
velas, indicadores, zonas, estrategias, IA, órdenes, posiciones, persistencia, replay
y laboratorio.

======================================

- Plan técnico §4 "Contratos y catálogos versionados (objetivo, ACT-C-001)":
  contrato común de estrategia, indicadores y datos para backend, UI e IA;
  catálogo dinámico completo como ampliación.
- Plan acción §5 fila ACT-C-001: mapa canónico de entornos, capacidades, velas,
  propuestas, órdenes y posiciones; contratos y catálogo común para UI/IA.
- Plan técnico §2 "Entornos separados": PAPER (datos reales, ejecuciones simuladas),
  EXCHANGE_DEMO (demo/testnet oficial), LIVE (fuera de alcance).
- Plan acción §10 "Bloqueos": distinguir datos ilustrativos, procedencia, entorno y
  capacidad operativa.

Este microtask **no implementa** el catálogo dinámico completo ni los contratos de
velas/órdenes/posiciones. Solo fija la base de entorno y capacidades sobre la que
esos contratos posteriores se apoyarán.

DECISIONES PENDIENTES CON RECOMENDACIÓN E IMPLICACIONES
========================================================

D1. ¿Unificar o separar los dos `Environment` de config y models?
------------------------------------------------------------------
Decisión: **excluido de este slice**.

No afirmar que existe una fuente única de verdad hoy: el repo contiene duplicados
en `config.py` y `models/state.py`. Unificarlos requiere migrar imports en múltiples
módulos y validar compatibilidad — fuera del scope de capacidades estáticas.

Este microtask define solo el contrato de capacidades (capítulo D2-D5). Si se decide
unificar Environment en un slice posterior, el contrato aquí definido no se ve afectado
porque usa `environment: Literal["paper", "exchange_demo"]`, independiente de la identidad del tipo.

D2. Estructura del inventario de capacidades (compatibilidad con `/api/capabilities`)
--------------------------------------------------------------------------------------
Recomendación: **estructura plana compatible con el endpoint actual**, sin romper la API.

El contrato debe reflejar los campos que `GET /api/capabilities` devuelve hoy:
  - `schema_version`: `Literal["backend_capabilities.v1"]` — versión del schema de capacidades, idéntica al valor actual del endpoint.
  - `environment`: `Literal["paper", "exchange_demo"]` — entorno runtime (sin modificar los enums existentes).
  - `runtime_health_checked`: `Literal[False]` — siempre False en este slice (sin diagnóstico), mantenido en su ubicación JSON actual para no romper compatibilidad. Se describe como metadata semántica, no anidada ni con promesa de transición automática a True.
  - Campos booleanos de soporte: `market_data_supported`, `technical_analysis_supported`,
    `ai_scenarios_supported`, `original_method_supported`.
  - Campos booleanos de ejecución/cartera/simulación: `execution_available`,
    `portfolio_available`, `paper_simulation_available`, `exchange_demo_execution_available`,
    `live_execution_available`.

Implicaciones: la estructura actual (planos booleanos) se mantiene como base. El contrato
canónico declara estos campos con sus tipos y semántica, pero no introduce jerarquías ni
subobjetos que requieran migrar consumidores existentes. La compatibilidad es por diseño:
los consumidores actuales de `/api/capabilities` siguen funcionando sin cambios.

D3. Aptitud de datos y disponibilidad de ejecución
----------------------------------------------------
Decisión: **excluidos de este slice**.

`data_aptitude` requiere un mecanismo de evaluación de frescura/health que implica
diagnóstico en tiempo de ejecución — fuera del alcance de capacidades estáticas.
`execution_available` como enum (paper | exchange_demo | none) requeriría migrar los
campos booleanos actuales y actualizar todos los consumidores.

Estos campos se dejan para un slice posterior donde se defina el mecanismo de evaluación
y se planifique la migración del endpoint `/api/capabilities`.

D4. Versión del schema de capacidades e inmutabilidad de `schema_version`
--------------------------------------------------------------------------
Recomendación: usar `"backend_capabilities.v1"` como versión del contrato canónico,
**idéntica al valor actual del endpoint**. No declarar una versión distinta que rompa la
compatibilidad JSON con `/api/capabilities`.

**Garantía de inmutabilidad**: `schema_version` se define como un campo Pydantic de tipo
`Literal["backend_capabilities.v1"]` con `Field(frozen=True)`. Al ser Literal, el único
valor aceptable es `"backend_capabilities.v1"`; al ser frozen, no puede reasignarse tras
la construcción. No usar `ClassVar`: ese tipo no aparece en la respuesta JSON y rompería
la compatibilidad del endpoint.

Los consumidores (UI, IA) validan `schema_version` antes de interpretar campos. Si la
versión no coincide con `"backend_capabilities.v1"`, se rechaza el payload o se activa un
modo fallback.

D5. ¿Incluir `runtime_health_checked` en el contrato canónico?
---------------------------------------------------------------
Recomendación: **sí, como campo plano en su ubicación JSON actual**, no como metadata anidada.

Valor actual: siempre False porque el endpoint no diagnostica. El contrato debe mantenerlo
en su posición plana (no dentro de un subobjeto `metadata`) para no romper compatibilidad.
Se describe como metadata semántica, pero no se promete que pasará a True automáticamente
ni se anida en ningún subcampo.

Implicaciones: no bloquea la implementación del slice; documenta una capacidad futura
sin comprometer a implementarla ahora.
